ERP 侧 Kafka 事件产生规则

（Event Emission Rules from ERP）

1. 本规则的定位

本规则用于明确 ERP 系统在何种业务条件下，才被允许向 Kafka 发布业务事件。
其目的不是驱动业务流程，而是 对已经完成的业务判断进行事实性通知。

ERP 在本架构中 不是流程编排者，也不是状态机的驱动者，而是业务事实的确认者（System of Record）。

2. ERP 发 Kafka Event 的基本原则（不可违反）

ERP 向 Kafka 发布事件时，必须同时满足以下原则：

ERP 不得基于系统处理结果自动推导业务判断。
Kafka Event 仅能表示 “已被人或业务规则正式确认的事实”。

ERP 发布事件的行为，等价于在说：

「该业务事实已在 ERP 中被确认，且可被外部系统引用」

3. Kafka Event 产生的共通前置条件

任何 ERP 侧 Kafka Event 的发布，均必须满足以下条件：

（1）业务判断已完成

该事件所代表的业务判断，必须已经由 明确的判断主体 完成。
判断主体可以是业务人员，也可以是明确配置的业务规则，但必须可追溯。

（2）ERP 中存在最终确认状态

ERP 内部必须存在 不可逆 / 已确立的状态标志，例如：

「契約確定」

「決済完了」

「引渡完了」

若 ERP 仍处于「处理中」「仮登録」「確認待ち」等状态，则 禁止发布 Kafka Event。

（3）存在可引用的 ERP 证据

ERP 必须能够提供：

ERP 系统名

ERP 内的业务对象 ID

确认时间

这些信息必须被包含在 Kafka Event 的 erpConfirmation 中。

4. 各 Kafka Event 的具体产生规则（强制）
4.1 ContractConcluded

允许发布条件：

契约状态 = 「確定」

契约记录不可再编辑

ERP 销售管理模块中存在契约完成标志

禁止发布条件：

仮契約

再审核中

条件未明确的契约

ERP 的立场：

「契约这一业务事实，已经在 ERP 中成立」

4.2 PaymentCompleted

允许发布条件：

入金状态 = 「入金確認済」

决済处理已被会计人员承认

金额与契约金额一致（或在允许差异范围内）

禁止发布条件：

仮入金

未对账

处理中、部分入金未承认

ERP 的立场：

「该决済已被会计责任者确认」

4.3 TransactionCompleted

允许发布条件：

引渡 / 履约状态 = 「完了」

库存 / 引渡记录已关闭

不存在未结事项（欠品、返品待ち等）

禁止发布条件：

部分完成

例外处理未完了

法务 / 返金处理中

ERP 的立场：

「本交易已在业务上完全结束」

5. ERP 不得发布 Kafka Event 的场景（明确禁止）

ERP 在以下场景 严禁 发布 Kafka Event：

仅因批处理完成

仅因数据同步成功

仅因状态字段发生变化

系统自动补正、回填、修复数据

这些行为 不代表业务判断完成。

6. Kafka Event 发布的时点规则

Kafka Event 必须：

在 ERP 事务 提交成功之后 发布

与 ERP 数据更新 逻辑上原子

允许「至少一次」发布，但事件必须具备幂等性

7. 责任切分（最重要）

ERP 发布 Kafka Event 的行为，意味着：

ERP 对该业务事实的真实性负责

下游系统 不再进行二次判断

若业务事实有误，必须通过 补偿事件 而非回滚事件修正

8. 本规则在整体架构中的意义

通过本规则：

状态机只处理 事实

Kafka 只传递 判断结果

ERP 只承担 确认责任

责任边界可审计、可说明、可追责

9. 一句话总结（架构宣言）

Kafka Event 不是“发生了什么处理”，
而是“哪些业务事实已经被确认”。
